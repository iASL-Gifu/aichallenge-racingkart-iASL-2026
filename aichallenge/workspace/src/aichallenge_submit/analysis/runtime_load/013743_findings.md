# 013743実行：区間別負荷の調査

添付ログには別途の依頼文はなく、前回に続く原因調査として解析した。42集計窓・212.886秒・2046周期。2024周期（98.9%）で周期待ちを除く処理が25ms超過。平均9.61Hz。Fallback操舵所有415周期（周期数比20.3%、時間割合ではない）。

## ログで確定できる重い区間

5秒窓内の中央値。部品ごとの中央値は足して総時間とはしない。

WP187の車線判断は制御スレッドCPU時間だけでも中央値42.293ms、安全判定等は23.107ms。どちらも実時間との差があり、スケジューリング/GIL/I/O等の待ちも疑われるが、外部負荷だけの問題とは説明できない。

WP192付近では車線判断113.990ms、安全判定等57.626ms。対象d2が42mの解除距離を超え、Raceへ戻った直後に上表右側の値へ低下。別の追い越し区間WP245でも車線判断98.884ms、安全判定等60.340msへ再上昇。処理の分岐に強く依存する負荷であり、GPU使用率だけを原因とする説明には合わない。

地図更新やコマンドpublishは主な数十〜100msの増加箇所ではない。ただし車体マーカー等は通常時にも10ms程度あり、40Hzの予算25msに対して無視できない。本番MPCの余裕も少なく、最重部だけを改善して全周期25ms以内に必ず収まるという結果ではない。

## ソース照合と改善候補

具体的な関数別の実行時間・呼び出し回数は今回の計測にないため、以下は候補であって測定済みの犯人ではない。

1. `_center_frenet()` → `project_to_closed_path_frenet()`は毎回Center全354区間をPythonで走査する。`_center_longitudinal_between()`はこれを自他車の2回行う。`_relative_lane_vehicle_samples()`などから現在位置・将来位置を繰り返し投影しており、両方の重い区間に利用される。低負荷のローカル単体計測は1投影約0.113ms（500回平均）。実走行環境の時間や実呼び出し回数は未測定。
2. `_vehicle_passage()`／`_latched_target_passage()`などの対象通過判定、`_prediction_is_clear_of_vehicle()`などの予測衝突確認が複数の判断で再利用される。1周期内で同じ入力を再計算していないか確認する価値が高い。
3. 車体マーカーは周期ごとに構築・publishし、ログのthrottleはマーカー生成自体を間引いていない。視覚化のみの低頻度化は候補。衝突判定の周期を下げる変更とは分ける。

最初の修正候補は判定の削除ではなく、Center射影の事前配列化と同一入力の再利用。同一周期でも本番MPCやShadowが予測を更新するため、予測安全判定のキャッシュは単なる対象ID・周期番号だけでは不足する。本番解の世代、経路、対象スナップショット等の同一性を条件にする必要がある。

L0事前参照は今回も配置検証エラーで無効。今回の計測を新L0参照の効果として評価しない。

この調査では制御コードの変更は行っていない。
