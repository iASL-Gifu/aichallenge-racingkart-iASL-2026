# 011307実行の調査

40個のControlTiming窓、202.644秒、2071制御周期を集計。2053周期（99.1%）で待ち時間を除く処理が25ms超過。平均約10.22Hz。Fallback操舵所有は614周期（29.6%、時間割合ではない）。

## 確認できたこと

MPC外の制御処理が大きな時間を使っている。例えばログ2164行の5秒窓は試算ゼロ、本番MPCは50回全てsolved。それでもwork_wall中央値95.284ms、制御スレッドCPU54.947ms、non_mpc_work中央値85.021ms、本番MPC中央値10.679ms。MPC成功だけでは周期は回復しない。

ログ2886行の窓では試算ゼロでwork_wall185.476ms、non_mpc_work165.715ms、本番MPC18.073ms。部品ごとの中央値は単純に足し引きできないが、MPC外の負担が大きいという傾向は明確。

プロセス全スレッドのCPU利用は102.3〜108.1%（1コア100%換算）。機器全体のCPU利用率ではない。制御スレッド自身のCPU時間が25msを超える窓が多く、外部プロセスの待ち時間だけでは説明できない。一方、実時間とthread CPUの差も大きく、CPUスケジューリング、GIL、I/O、ロック等の待ちが上乗せされている可能性がある。ホストCPU/GPUログが添付されていないため、その内訳は不明。

試算は全体で114回、本番2071回。試算ゼロの窓でも100ms以上の遅れがあるため、Shadowだけを減らしても解決しない。特定窓では試算36回があり、局所的な追加負担はある。

指令publish間隔は最大475.339ms、指令stampの経過時間は最大430ms。現在コードは周期前半で取得したposeを使い、固定操舵遅延予測後に判断とMPCを行う。今回の大きく変動する処理遅れは、操舵判断の古さを増す要因になる。ただし、このログだけで各壁接触が遅延起因と確定するわけではない。

## 最後の停止

WP252でFallbackの現在地点チェックが`e_y=-3.407, allowed=[-3.158,2.458]`、約0.249mの範囲超過となっている。Pure Pursuitの前進確認を通らずlegacy_feedback・速度0になる。MPCもprimal infeasibleが継続する。StraightReentryが後退を試みるが`localization_inconsistent`で中断される。

これは「前方レーンが幅不足だから停止」とだけ説明する状態ではない。現在姿勢からの復帰と自己位置整合が問題になっている。物理壁との実接触そのものはこの横位置ログだけでは確定しない。

L0事前参照は今回も読み込みエラーで無効（598行）。この走行は新参照の性能評価にはなっていない。

## 次に必要な切り分けと追加計測

今回の`non_mpc_work`だけでは、特定の関数を犯人と断定できない。ソース上はV2X更新ごとの地図再構築、車体マーカー生成・publish、車線判断、繰り返す衝突予測、安全判定・Fallback等が含まれる。安全判定を削除して速度を上げる変更はしない。

既存の5秒集計にstageの実時間/thread CPU時間を追加した。

- `stage_v2x_map_*`：V2Xスナップショット、予測障害物、地図更新
- `stage_pose_body_visualization_*`：経路topic更新の分岐、姿勢取得・車体マーカー生成とpublish
- `stage_pre_lane_state_*`：車体表示後から姿勢更新までの状態処理
- `stage_lane_decision_*`：車線・速度等の本番MPC前の判断
- `stage_live_mpc_*`：本番MPC呼び出し
- `stage_safety_fallback_*`：本番MPC後の衝突・速度・Fallback等の判断
- `stage_command_publish_*`：車両状態更新とコマンドpublish
- `stage_tail_or_early_return_*`：描画・走行記録などの末尾、または最後のチェックポイント後の途中return処理

stageは区間の包括時間なので、車線判断内の試算はstageにもprobe_mpcにも入る。両者を足して総時間にしない。途中returnした周期は後続stageに件数が出ない。stageの記録は既存ControlTiming行に含め、別途高頻度のログは追加しない。
