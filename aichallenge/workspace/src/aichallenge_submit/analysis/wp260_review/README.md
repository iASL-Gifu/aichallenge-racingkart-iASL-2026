# WP230–280 静的経路・境界の診断

現行configで指定されたCenter CSVと境界CSVを読み、実際のget_lane_boundsメソッドを抽出して3車線分割を再現した。WPはCSVの0始まり行番号。_construct_pathは再サンプルせず入力点を使用する。yawは実装と同じ次点への方向、法線はyaw+π/2。OUTER_COURSE_MARGIN=0.7mを反映。車線目標は各境界区間の中点（_compute_lane_centerと同じ位置）から再構成した。

geometry.pngは静的な名目目標と境界であり、本番MPC解やシミュレータ実測壁を再現するものではない。曲率は隣接3点の外接円による幾何推定であり、実コードがCenterに保存する平滑化済みkappaとは区別する。

## 結果

- ホイールベース1.087m、モデル舵角上限18度から曲率上限tan(18°)/1.087=0.2989 1/m、最小半径3.345m。
- WP230–280のCenter点列は最大曲率0.2027 1/m（WP261）、必要舵角約12.43度。
- L0の中点列は最大0.4908 1/m（WP257）、必要舵角約28.08度。WP251,256,257,260,263,266で0.2989を超える。
- L0横目標はWP250で−3.134m、WP255で−1.363m、WP256で−0.600m、WP257で−0.248m。境界幅による分割が切り返しを急にする。
- L0の推定舵角差分から7.5m/s時に最大約4.50rad/sを要求。controllerがMPCに渡す制限は2.25/1.68=約1.34rad/s。舵角上限を無視して速度だけ落とす解決はできない。
- L1/L2中点列も局所的な曲率スパイクがあり、単純なレーン番号の置換だけでは目標生成の問題は解決しない。
- L0進入禁止の設定はWP230–255。最大曲率のWP257はその直後。別にouter_lane_mpc_problem_zones=238–265が存在する。

## 実装上の原因候補

get_lane_boundsは点ごとに幅を分割するだけで、連続性・曲率・車体の掃引形状を制約しない。_compute_lane_centerはこの区間の中点を横目標にする。MPCの線形化・入力参照はCenter曲率を基準とし、横目標の曲がり方を同じ目標曲率として直接与える構造ではない（予測曲率による速度制限は別に存在）。点ごとの幅成立は、その目標を操舵制限内でつなげることの証明にならない。

MPCは目標を必ずそのまま追うわけではないため、この計算だけでMPC解の制約違反やL0内の全経路の不成立を断定できない。またCSVの点・横余裕だけでは長い車体の角と突起の干渉を確定できない。ライブ境界・実車姿勢による非線形ロールアウトと車体矩形の連続確認が必要。

## 推奨

1. 実境界を保ったまま、周辺区間全体で車線参照を曲率制約付きで生成する。最適化するのは経路であり、突起の境界自体を平滑化して消してはいけない。
2. 横位置・目標方位・目標曲率を同じ経路から生成し、操舵角・操舵速度・遅延・車体掃引を検証する。
3. 可行な形状に対して速度プロファイルを作る。舵角上限を超える形状は低速化だけで救済しない。
4. 現在WPだけでなく、進入から区間通過までの接続可否でL0を許可する。検証できるまでは現在の禁止を外さない。
5. MPC解が不成立、あるいは代替操舵の壁検査が失敗した際に、未検証の旧フィードバックで前進を継続する問題は別途直す。
