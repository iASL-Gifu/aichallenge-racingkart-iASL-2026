# 追越し時の停止・減速の原因調査

対象: 現在のaichallenge_submitとaichallenge_submit_old、および添付ログ7442行。
ログ: `/home/takenoyama/.codex/attachments/fad22d8f-f52c-46e8-9909-ad84362d5699/pasted-text.txt`

結論: 今回の走行では、前回の適合実装で追加したunknown判定が、速度の一時的な無効化をレーン全体の危険に拡大し、追越し状態を繰り返し破棄していることが最も強く示される。Oldの未移植機能だけが原因ではない。前回の安全側への適合が広すぎた箇所を先に直すべきである。

## 1. 速度不明を対象の幾何情報不明として扱い、走行可能なレーンを解除する（最優先）

現在 `mpc_controller.py:2105` の `_committed_target_body_overlap()` は、`has_velocity_estimate(target_id)` がfalseだと、位置が存在してもNoneを返す。呼出し側の `:2124` はこれを `target_geometry_known=False` とし、`overtake_lane_hold.py:58` 以降で即時unsafeかつphysical_passage_lostにする。

解除側 `mpc_controller.py:9920` 以降では、HybridとShadow検証を破棄して全幅回復に入り、physical_passage_lostなら左右両方を回復候補から除外する。一周期の速度不明が、横移動中断、L1/全幅回復、安定待ち、再Shadowにつながる。

Old `mpc_controller.py:10065` 付近は、現在車体の実際の重なりを解除条件にする。現在のように速度有効性を別の必須条件として加えた解除ではない。またOldはbraking_unknown_idsを解除へ反映していないが、これは別途対処すべき安全上の穴であり、そのまま戻せばよいという意味ではない。

ログの明確な例:

- 960〜981行: d2にShadow確認済みでL0確定。Hybridが3m進んだところで、幅有効・左右通過可・競合なしなのにtarget_geometry_unknownで解除。直後に対象速度0m/s、指令上限0.54m/sになる。
- 2248〜2256行: d3に同じ理由でL0解除。横距離4.86m、横余裕+3.34m、ego L0 / target L2にもかかわらず、対象速度0m/sとしてcritical_or_stoppedに入り0m/sを要求。次のログでは対象速度3.53m/s、その後EmergencyBrakeSkipへ戻る。
- 2358〜2364行: 対象まで16.92mあり、L0通過可・競合なしでも解除して再び速度合わせと回復待ちに入る。

速度ゼロの根本的な引き金は、添付ログだけでは確定できない。V2X各車のサンプル時刻・有効性理由が出ていないためである。ただし実コードによる小規模再現では、4m/sの有効推定後に同じ時刻・同じ位置を再度updateするだけで、速度が0・valid=Falseとなり、上記target_geometry_unknown解除を再現した。

`v2x_vehicle_tracker.py` はdt<=0を無効としている。0.20秒のゼロ補間はdt>0の正常観測にのみ適用されるので、重複時刻は救済されない。このdt<=0無効化自体はOldにもあり、新しい解除条件との組合せが問題を増幅する。位置飛び・過大速度の警告は添付ログでは見つからないが、それだけで重複時刻が原因と断定はできない。

さらにEmergencyBrake側は保持中のCenter予測ハザードがあると横方向の単純なSkipを通さず、`velocity()`のゼロ値で停止車用の式へ進める。これが「解除だけ」で終わらず急減速に結びつく経路である。Center予測ハザードや停止車用の式はOldにもあるため、単独の新規差分ではない。

修正方向: 観測の重複・時刻巻戻り・本当の欠測・異常速度を区別する。最新位置の幾何判定と速度推定の確からしさを分け、速度の一時欠落だけで物理幅喪失や左右両候補の禁止に変換しない。不明速度を停止車速度ゼロとして扱う経路も併せて見直す。

## 2. 関連性を判定する前に全active車のunknownで解除する（最優先）

現在 `mpc_controller.py:2050` の `_committed_lane_traffic_evidence()` は、固定窓外の高速接近車も検出するため全active車を候補にしている。その際、サンプル欠落や車線不明を、距離・選択レーンとの関連性を確かめる前にunknownへ加える。

ログ7344〜7347行では、d3と並走しL0/L2とも通過可・競合空なのに、d2のunknownでL0解除し、直後にL2向きの全幅ガイダンスが始まる。7354行では再びL0へ再試算しており、見た目の迷いに直結する。

実メソッドの再現でも、200m先に置いた車の車線判定をNoneにするだけで、選択レーンが通過可能でもunknownによる解除となった。実ログのd2が遠方だったか、速度・車線・距離のどれがunknownだったかは記録不足で断定できない。

修正方向: 対象外の車について、選択レーンへの侵入可能性・現在位置・距離・到達可能範囲で関連性を先に判定する。関連する後方車の速度不明は引き続き保守的に扱う。一方、関係を否定できる遠方車まで一律に解除理由としない。ログにはunknownの内訳を残す。

## 3. 完了判定でHybrid維持条件が消える（実ログで確認、Oldにも共通）

現在 `mpc_controller.py:4847` はCenter移動距離が移行距離の98%以上になるだけでcompleted=Trueにする。実際の横位置到達は完了条件に含まれない。

`:2140` 付近の維持判定はnot completedを必要とするため、完了直後にprogressが0扱いになり、35%維持条件が消える。対象由来の余裕喪失が既に0.40秒続いていれば、完了直後に解除できる。

ログ7144〜7161行: L0の進捗85%ではlocked=True。その後9.99/9.43mでHybridCompleted。直後にMPC境界幅0で失敗し、progress=0、target_clearance_lostで全幅解除している。レーン到達前に参照上の移行終了と継続保護が終わる可能性がある。

Oldも距離98%完了・not completedによるロック条件を持つ。したがってこれは今回悪化した差分としてではなく、双方に残る問題として扱う。

また7359〜7361行では追越し物理完了通知の直後に旧対象の継続監視が再び解除を要求している。完了と旧ラッチ監視の実行順序も回帰対象に加える必要がある。原因の確定には同一周期の状態記録が必要。

## 4. Oldにある、移行中の停止からの微速脱出が未移植（条件次第の原因）

Old `mpc_controller.py:12694` と `v2x_vehicle_tracker.py:972` には `hybrid_lateral_escape_creep_allowed()` がある。有効な低速対象・アクティブHybrid・車体非重複・横車体余裕0.10m以上・候補通過可・front/side競合なしを満たす場合、厳格Shadow微速条件が使えなくても0.6m/sの脱出を認める。

現在版は `mpc_controller.py:12412` の厳格Shadow微速のみで、この第2経路がない。空間Hybridは停止すると実移動進捗が増えないため、回復後などに証明が切れていると「横へ逃げるには前進が必要だが、前進速度がゼロ」の状態に陥り得る。

添付ログには移行途中と0m/s要求の組合せがある。ただしその全部がOldの微速条件を満たすとは限らない。特に速度推定無効や車体重複を微速で突破してよいとは言えない。1と2を直した後に条件を検証する順番がよい。Oldの対象別SpeedPlanによる制限解除も関係するので、単純に最終速度をmax(0.6)へ変える移植は不適切。

## 5. 接近速度と地理的規制の差（確実な設定差、主因より後）

- 確定前速度余裕: 現在+0.5m/s、Oldは基本+0.8m/sに距離依存の最大+2.2m/s。35m時点では合計+3.0m/s、10m以下で+0.8m/s。
- 確定後の速度余裕: 現在+1.5m/s、Old+2.5m/s。
- 現在はL0禁止WP230〜255、Oldは空。ログ2531行以降にL1への置換が実際に出ている。
- 外側MPC問題区間: 現在WP238〜265、Old250〜262。Oldには全車両への例外許可設定もある。ログ2553行以降に全幅化が出ている。

前回は依頼の移植範囲に合わせて速度上乗せと地理規則を残した。そのためOldより遅く接近する差は残っている。特に準備だけ35mへ拡大し、速度合わせを+0.5のままにしたので、早くから低速追従する時間が増え得る。ただし一瞬で0m/sになる主要因を速度余裕の不足だけでは説明できない。

OldのMPC目標の外側余裕や予測境界回復にも未移植差分がある。今回のログだけではそれぞれの寄与を切り分けておらず、実際の解なしがあることから無条件にOldの制約緩和を戻すべきではない。
